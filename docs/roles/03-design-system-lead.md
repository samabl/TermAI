# TermAI 设计系统 & 视觉体验负责人评审意见

> 作者：设计系统 & 视觉体验负责人（Design System & Visual Experience Lead）
> 状态：评审稿 v1 —— 供 Orchestrator 仲裁，含显式取舍与冲突点
> 范围：视觉语言、Design Token、终端特有画质、主题生态、AI 输出视觉语法、设计-工程交付与度量

## 一、角色立场与判断依据

我代表"美观的可操作定义"和"视觉一致性"这条线。我的立场是：**TermAI 的第一性体验是终端，不是聊天窗口**；任何 AI 视觉表达都不得降低字符网格的可读性、可预期性和稳定性。我的一切判断依据三条硬约束：

1. **可量化**：美观必须能落到数值上——对比度、行高倍数、网格对齐误差、动效时长、帧预算、视觉回归阈值。落不到数值的审美争论我不参与。
2. **零漂移**：所有颜色/间距/圆角/字体来自单一 token 源，代码里不得出现硬编码色值。视觉回归是 CI 门禁，不是设计走查。
3. **性能是视觉预算的一部分**：任何视觉效果如果侵蚀 60fps 或输入延迟 <10ms，一律降级或砍掉。

代价：比"随手画界面"的团队慢，AI 富媒体表达偏保守——这是有意的。

## 二、关键结论

### D1｜渲染与 UI 分层：自研 wgpu 终端画布 + WebView UI 层（混合方案）
- **结论**：终端字符网格由 Rust/wgpu 自研渲染；周边 UI（设置、会话管理、AI 面板、插件市场）用 WebView + TS 组件库。不做全自研原生 UI，也不用 Electron。
- **理由**：不可妥协的画质点（字符网格、光标、选区、亚像素层）必须自控；设置/表单/列表用 WebView 迭代快数倍，TS 组件生态成熟。
- **代价与取舍**：两层渲染必须靠同一 token 源同时生成 TS 与 Rust 常量来强行统一；交付链多一层。不统一就会呈现"两个 App 拼起来"的廉价感——这是我最担心的失败模式。

### D2｜Token 是唯一真相源，含 AI 语义色阶
- **结论**：`tokens/*.json` 为源，codegen 出 TS（CSS 变量 + const）、Rust const、主题 JSON schema、文档站。palette / type / space / radius / elevation / motion / AI-semantic 七组，全部语义命名（`bg.canvas`、`fg.muted`、`ai.risk.critical`），禁止在组件里写原始色值。
- **理由**：主题生态、浅/深/高对比、第三方主题导入全部依赖这层抽象；没有它，主题生态是空想。
- **代价与取舍**：初期建 pipeline 的时间比直接写 CSS 慢；Rust 侧需要接受生成常量的编译期依赖。我坚持这一点，宁可推迟首批 UI 页面。

### D3｜终端画质：字形优先，放弃 GPU 亚像素抗锯齿
- **结论**：默认灰度抗锯齿 + hinting 关闭 + 网格对齐；提供"锐利/柔和"两档。**不承诺 ClearType 式 subpixel AA**。主字体 JetBrains Mono（含 ligature，默认开启，可关），Nerd Font 图标回退，CJK 独立回退栈。
- **理由**：GPU 上 subpixel AA 与透明背景、缩放、非整数 DPI 存在根本性冲突，会导致各平台画质不一致。
- **代价与取舍**：Windows 用户会感到"不如 Windows Terminal 锐利"。我用超采样与网格对齐补偿，但这是明确的功能性损失，需写进已知问题。

### D4｜AI 输出是"结构化视觉语法"，不是卡片堆砌
- **结论**：定义一套 AI 输出原语——Inline Hint、Command Explain（侧栏流式）、Diff Block、Diagnosis Card、Risk Ladder——由 AI 输出的结构化 schema 驱动渲染，不允许自由 markdown 直出。风险四级：info(蓝)/caution(黄)/danger(橙)/destructive(红)，且 destructive 必须二次确认。
- **理由**：自由渲染会立刻破坏终端的信息密度与信任感；风险色阶是安全边界，不是装饰。
- **代价与取舍**：AI 表现力被 schema 限制，模型输出的富文本需降级映射。与 AI 体验负责人必然冲突（见第五节）。

### D5｜签名视觉语言：暗底高对比 + 克制的"AI 微光"
- **结论**：主色不用终端烂大街的霓虹绿，用冷青/靛蓝作为唯一 brand accent；强调色只用于焦点、AI 活跃态、链接。圆角统一 4/8/12 三档。动效统一 120/180/240ms + `ease-standard` 曲线，高对比模式与"减动"偏好下全部退化为即时。
- **理由**：品牌辨识度靠一致的克制，不靠炫技；动效服务于状态变化，不服务于表演。
- **代价与取舍**：视觉上不如竞品"炫"，演示视频不占便宜。接受。

### D6｜许可与商业：核心开源(Apache-2.0) + 商业版增值，主题永久免费
- **结论**：终端内核与设计系统开源；团队协作/云同步/企业策略为商业版。**主题格式与主题商店永久免费且开放**，第三方主题不经过审核即可本地导入。
- **理由**：终端信任来自可审计与可脚本化；主题是网络效应，收费即死。
- **代价与取舍**：放弃主题变现，并承担恶意主题的安全成本。

## 三、详细设计

**1. Token 规格（摘要）**

| 组 | 关键规格 |
|---|---|
| 色板 | 3 层：primitive(灰阶 12 级 + 8 色相 × 6 级) → semantic → component。深色为默认，浅色/高对比同 schema |
| 字体 | 等宽 JetBrains Mono / 图标 Nerd Font Symbols / CJK 系统栈；字号阶梯 12·13·14(默认)·16·18·20；终端字号独立可调 |
| 间距/圆角 | 4px 基准，4·8·12·16·24·32；圆角 radius-sm 4 / md 8 / lg 12，终端画布圆角为 0 |
| 层级/阴影 | elevation 0-3，深色主题用"亮边 + 低透明阴影"而非纯黑投影，避免脏 |
| 动效 | duration 120/180/240ms，ease-standard=(0.2,0,0,1)，ease-out-quart 用于进入 |
| AI 语义 | `ai.risk.{info,caution,danger,destructive}`、`ai.stream.cursor`、`diff.{add,del,ctx}` |

**2. 终端视觉品质（硬指标）**：字符网格按字体 EM 盒与 advance width 精确对齐，误差 ≤0.5px；默认行高 1.25，可调 1.0–2.0；光标默认块状 + 200ms 呼吸（可关），失焦变空心；选区在深色下用 accent 30% 透明度，且必须保证反白后文字对比度 ≥4.5:1；背景模糊/透明仅在合成器支持时代价计费，默认关闭，并提供"性能安全模式"一键关闭全部模糊与动效。

**3. AI 视觉语法**：解释与诊断默认进侧栏（不挤压终端），diff 与错误可内联但**行数 >40 或被折叠时不计入终端 scrollback**；流式输出用统一光标与"未完成"底纹，禁止逐字闪烁；风险色阶与 `destructive` 的二次确认由组件强制，AI 不得绕过。

**4. 主题系统**：主题 = token 覆盖文件（JSON，JSON Schema 校验 + 版本号 + 可选签名）。官方提供 Dark/Light/High-Contrast 三套 + 跟随系统（含 Windows/macOS 独立监听 + 定时切换）。导入失败必须给出"哪一行哪个 token 非法"的明确报错。主题不得注入脚本或自定义 CSS。

**5. 交付流程**：tokens → codegen（TS/CSS/Rust）→ 组件库（Storybook + 视觉测试）→ CI 中 Playwright 截图 + 像素 diff 门禁。所有视觉 PR 必须带截图。

## 五、被否决的方案与反方意见

| 被否方案 | 反方最强理由 | 我为何仍否决 |
|---|---|---|
| 全自研原生 UI（候选 A） | 画质与性能完全可控，无 WebView 抖动 | 设置/表单/列表迭代成本极高，视觉一致性靠人肉，长期维护差 |
| Electron + xterm.js（候选 C） | 生态最成熟、最快出产品 | 终端画质与输入延迟无法达到世界级；内存占用与品牌定位冲突 |
| AI 输出全部卡片流 | 表达力强、演示效果好、用户易懂 | 把终端降级为聊天窗口，摧毁信息密度与专业用户信任 |
| 完全兼容 iTerm/Ghostty 主题格式 | 白嫖生态，导入零成本 | 格式无法承载 AI 语义色与组件 token，长期被锁死 |
| GPU subpixel AA | Windows 观感更锐利 | 与透明、缩放、跨平台一致性根本冲突，见 D3 |
| 主题商店审核制/收费 | 可治理质量、有收入 | 扼杀网络效应，违背终端社区信任模型 |

**预期冲突点（请 Orchestrator 仲裁）**：①与渲染负责人就 subpixel AA 与画质档位的取舍；②与 AI 体验负责人就"卡片 vs 侧栏/内联"的边界；③与性能负责人就模糊、动效、阴影的成本；④与架构负责人就 WebView 层是否引入"两套视觉"风险。

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| WebView 跨平台渲染差异 | 锁定单一 WebView 版本 + 每平台基线截图 |
| 字体回退致网格错位 | Rust 侧实测字形宽度；CJK 双宽契约；可选自带字体 |
| 动效/模糊过量 | 默认减动、高对比禁用、性能安全模式一键全关 |
| 恶意主题 | 主题纯数据、Schema 校验、无脚本、可选签名 |
| token 与代码漂移 | CI "零硬编码色值"检查，codegen 失败即阻断 |
| AI 卡片堆积稀释终端 | schema 白名单 + 侧栏优先 + 不计入 scrollback |

## 七、可验证验收标准

1. 对比度：正文 ≥7:1，次要文字 ≥4.5:1，`destructive`/背景 ≥4.5:1（CI 校验全部主题）。
2. 视觉回归：Playwright 截图 diff ≤0.1%，非白名单区域零变化。
3. 性能：UI 交互 60fps（单帧 ≤4ms）；终端输入到上屏 ≤10ms（P95）；冷启动可交互 ≤300ms。
4. token codegen 覆盖率 100%；仓库硬编码色值 = 0（CI 阻断）。
5. 字符网格对齐误差 ≤0.5px；行高默认 1.25；字号 12–20 全档无错位。
6. 主题导入：合法 100% 成功；非法 100% 报错并定位到具体 token。
7. "减动"偏好与高对比主题下，全部动效退化至 ≤16ms。

## 八、待决议问题（Open Questions）

1. 品牌主色取向：冷青 vs 靛蓝？是否允许双 accent？
2. 是否允许高级用户覆盖 token 与自带字体（自担画质风险）？
3. 本阶段是否正式放弃 subpixel AA 并写入已知问题清单？
4. AI 输出默认落点：侧栏为主还是内联优先（需 AI 体验负责人共同定稿）？
5. 高对比模式是否跟随系统 API（Windows 高对比 / macOS 增强对比）？
6. 主题格式是否对外发布 JSON Schema 并承诺语义化版本兼容？
7. Web/远程形态下，token 与组件库是否需独立切片？
