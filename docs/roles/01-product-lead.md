# TermAI 产品评审意见（CPO / 产品负责人）

## 一、角色立场与判断依据

我负责 TermAI 的最终用户体验与商业结果，排序函数是：**用户长期留存 > 不可复制的差异化 > 工程优雅 > 首版交付速度**。三条判断公理：

1. **终端是信任基础设施。** 用户把生产服务器、集群、数据库交给我们。一次 AI 误操作（误删、误推分支、改错 K8s context）造成的信任损失，无法用一百个新功能弥补。
2. **终端本质仍是三件事：延迟、正确性、可脚本化。** AI 是放大器，不是遮羞布；VT 序列、宽字符、IME、剪贴板有一处不对，AI 再好也没人用。
3. **AI-native 的定义是"状态结构化"，不是"接了大模型"。** 只有当会话、命令块、退出码、文件系统、Git、容器状态都成为 AI 可读写的结构化对象时，AI 才是原生；否则只是外挂。

我拒绝把"美观、功能丰富"当作定位——那是结果，不是差异。

## 二、关键结论（D1–D8）

**D1｜AI 是一等公民，但"聊天框"是底层层级。**
- 结论：AI 与终端共享同一 Session/Event 模型，是上下文总线上的一个可编程 actor；主交互是 **inline、命令级、可 diff、可审批、可回滚** 的动作，自然语言聊天是兜底 UI 而非主入口。
- 理由：聊天框是零差异形态，任何终端一周能抄；护城河在"AI 能读到什么、能否安全写回、能否审计回滚"。
- 代价：会话模型必须第一版就事件化/结构化，架构成本前置；首版"看起来"比竞品少功能。

**D2｜技术栈：Rust 核心 + wgpu 自研渲染 + 原生 UI，拒绝 WebView 做主路径。**
- 结论：采候选 A。终端网格、UI chrome、AI 面板同一原生渲染栈；WebView 仅用于未来的文档/网页预览等非关键路径。
- 理由：网格渲染是核心资产，WebView 在 IME、滚动、纹理直通、输入延迟上长期吃亏；双 UI 栈会带来永久不一致与技术债。
- 代价：UI 迭代慢于 Web 团队，招人面窄，插件生态需要额外机制补偿。

**D3｜插件 ABI 只认 WASM 沙箱。**
- 结论：第三方扩展唯一官方 ABI 是 WASM（WASI + 能力声明）；不开放任意 Node/Python 进程内插件。
- 理由：终端插件天然需要读进程、读网络、读文件，进程内插件等于把用户机器交给生态。
- 代价：初期生态冷启动困难，高质量插件作者迁移意愿低。

**D4｜商业模式：Open Core，核心开源，AI 服务与团队能力收费。**
- 结论：核心终端与基础 AI 能力 Apache-2.0；云端 AI、团队策略/审计/SSO、私有模型网关、企业合规为订阅。**永不出售用户数据，永不做本地功能的远程锁。**
- 理由：终端是可脚本化基础设施，闭源会失去工程师信任与包管理器分发渠道。
- 代价：存在免费 fork 分叉；壁垒必须建立在服务、数据网络效应与体验，而非源码。

**D5｜用户收紧为两个 Primary Persona。**
- 结论：Primary = SRE/平台工程师 + 高级软件工程师；Secondary = 数据/AI 工程师、CLI 爱好者。明确不做"零基础学终端"人群。
- 理由：两类用户的痛点是"上下文割裂 + 高危操作"，付费能力与传播力最强。
- 代价：放弃最大的教育市场（Warps/Wave 的战场），规模故事变难讲。

**D6｜北极星：Accepted AI Actions per Weekly Active User。**
- 结论：北极星为"每 WAU 每周被用户接受的 AI 动作数"，而非 MAU 或命令数。
- 理由：它同时约束 AI 的可用性与有用性，无法用刷 DAU 造假。
- 代价：指标与商业化收入非直接同构，需要配套先导指标。

**D7｜兼容优先于多路复用自研。**
- 结论：必须实现 Kitty graphics 与 tmux 键位/控制兼容；内置 session 持久化但**不强制**替代 tmux。
- 理由：SRE 的 .tmux.conf 与脚本是迁移门槛，强行替代等于拒绝这批人。
- 代价：长期背着兼容负担，内置多路复用体验被历史协议约束。

**D8｜明确不做的 anti-features 见 §三末。**

## 三、详细设计

### 3.1 定位与 JTBD

定位一句话：**"把从报错到修复之间的所有上下文，交给一个可审计的 AI。"**

| Persona | JTBD | 现状痛点 |
|---|---|---|
| SRE/平台 | 线上故障时快速定位并安全执行修复 | 上下文散落在 SSH、日志、K8s、聊天记录 |
| 高级工程师 | 在终端里完成构建-调试-提交闭环 | 命令历史不可检索、AI 无法读懂报错 |
| 数据/AI 工程师 | 长任务、环境、GPU 资源管理 | 会话丢失、环境不可复现 |

### 3.2 MoSCoW 功能矩阵

| 级别 | 功能 |
|---|---|
| **Must** | VT/xterm 全序列兼容；GPU 渲染；tab/分屏；Win/macOS/Linux PTY（ConPTY）；CJK/IME/emoji/组合字符正确；可搜索回滚；**结构化命令块历史**；AI inline 建议+审批+审计+回滚；MCP/工具调用；WASM 插件沙箱；配置即代码 |
| **Should** | 会话持久化/重连；Kitty graphics；Git/容器/K8s 上下文感知；团队共享配置；BYO/自托管模型；SSH 集成 |
| **Could** | Web 客户端；协作共享终端；移动端；云同步 |
| **Won't（本期）** | 自有 shell 语言；内置编辑器/IDE；AI 全自动免审批执行；终端内跑完整 Web 应用 |

### 3.3 竞争关系

| 对手 | 判断 |
|---|---|
| **Warp** | 唯一正面竞品，AI 工作流最成熟；但闭源、强制账号。我们打**开源核心 + 可审计 + 自托管模型**。 |
| **Windows Terminal** | 系统默认，Windows IME 标杆。**不争默认终端**，只争"专业用户主动安装"。 |
| **Ghostty** | 性能与原生标杆。我们**不能输延迟**，这正是 D2 选原生渲染的原因。 |
| **WezTerm** | 可脚本化标杆。继承其精神，用 TS 插件 API 替代 Lua（有争议，见 §五）。 |
| **Kitty / Alacritty** | 性能基准线，非直接对手；实现 Kitty 协议兼容以承接迁移。 |
| **iTerm2** | macOS 霸主。主攻对象：用 AI + 跨平台一致体验挖角。 |
| **Tabby** | 证明可扩展终端有需求，但 Electron 重。以原生性能收割。 |
| **Wave** | **反面教材**：重 GUI、偏教学。提醒我们不要变成 Web 应用。 |
| **Fig/Amazon Q** | 补全引擎，能力互补；可集成但**不依赖其云端**。 |
| **Cursor 终端** | 不与之争 IDE 内终端；反向通过 CLI/MCP 成为其**外部终端后端**，这是分发策略。 |
| **tmux/zellij** | 共存优先：兼容键位与协议，内置替代但不强制（D7）。 |

### 3.4 商业模式与许可

Open Core + 订阅：Free（本地全功能 + BYO key）→ Pro（云端 AI 额度、同步、高级插件）→ Team（共享配置、策略）→ Enterprise（SSO/SCIM、审计导出、私有模型网关、离线部署）。原则：**本地功能永不被远程锁死；插件市场抽成为可选而非唯一收入**。

### 3.5 路线图（按依赖，不按时间）

| 阶段 | 内容 | 可交付定义 |
|---|---|---|
| **P0 信任基座** | PTY/VT/渲染/跨平台 | vttest+esctest 全绿；P99 输入延迟达标 |
| **P1 上下文模型** | 命令块、结构化历史、脚本 API | 所有会话状态可经 API 读取 |
| **P2 AI 一等公民** | inline 建议、审批、审计、回滚 | 100% AI 动作可审计、可撤销 |
| **P3 生态** | WASM 插件、MCP、兼容层 | 第三方可无特权发布插件 |
| **P4 团队/企业** | 同步、策略、私有部署 | 无外网环境功能完整 |

## 四、与其他角色的接口与依赖

| 对象 | 必须给我什么 | 我承诺什么 |
|---|---|---|
| 内核/架构 | 事件化会话模型；延迟预算 | 冻结 UI 需求边界，不做中途改协议 |
| AI/ML | 动作 schema、审批分级模型 | 定义"可接受误操作率"与回滚 UI |
| 安全 | 威胁模型、沙箱边界 | 不因体验牺牲高危确认 |
| 插件平台 | 稳定 ABI 版本策略 | 承诺 2 个大版本兼容窗口 |
| 设计 | 交互与视觉规范 | 不牺牲键盘可达性与延迟换美观 |
| 法务/商业 | 许可与合规意见 | 明确 Open Core 边界并对外一致 |

**我预期的主要冲突点**：D2（原生 UI vs 架构师的 WebView 提速方案）、D3（WASM-only vs 生态负责人的开放插件）、D1 审批模型（分级自动 vs 安全角色的"全部确认"）、D4（开源 vs 商业化角色主张的闭源 SaaS）、D5（收紧用户 vs 增长负责人要教育市场）。请 Orchestrator 逐条仲裁。

## 五、被否决的方案与反方意见

| 方案 | 反方理由（保留） | 否决理由 |
|---|---|---|
| Tauri/WebView 主 UI | 迭代快、招人易、UI 表现力强 | IME/延迟/纹理直通长期吃亏，双栈技术债 |
| Electron + xterm.js | 生态成熟、最快出原型 | 内存与延迟无法达到标杆 |
| 完全闭源 SaaS | 收入直接、可控 | 失去终端信任与分发渠道 |
| 免费全功能 + 捐赠 | 增长最快 | 无法支撑长期 AI 成本与团队 |
| AI 全自动执行（YOLO 默认开） | 体验极致 | 一次事故摧毁信任 |
| 聊天框作主入口 | 易理解、易演示 | 零差异，注定"又一个带聊天框的终端" |
| 自研 shell | 完全掌控 | 与生态为敌，用户零迁移意愿 |

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| VT/IME 长尾（Windows CJK 最坑） | P0 建兼容测试矩阵并作为发布门禁 |
| AI 误操作摧毁信任 | 分级审批 + 全量审计 + 强制可回滚检查点 |
| 性能退化 | CI 中加入延迟/内存回归门禁 |
| 生态冷启动 | 官方先做 10 个高质量插件 + MCP 兼容红利 |
| 大厂免费夹击 | 差异化在可审计与自托管，而非价格 |
| 范围蔓延 | anti-features 写入产品宪法 |
| 许可被分叉 | 靠服务与网络效应而非源码设壁垒 |

## 七、可验证验收标准（尽量量化）

1. 输入到像素 P99 < 16ms；冷启动 < 150ms；120Hz 滚动无掉帧。
2. 10 tab 常驻内存 < 120MB。
3. vttest / esctest 通过率 100%；CJK/emoji/组合字符用例 100% 正确。
4. 崩溃后会话恢复率 100%。
5. AI 动作可审计率 100%，可撤销率 100%，高危动作拦截率 100%。
6. 上线 6 个月内，AI 建议接受率 ≥ 25%，Accepted AI Actions/WAU ≥ 5。
7. D7 留存 ≥ 40%；W4 留存 ≥ 20%。
8. 第三方插件无需特权即可发布，ABI 兼容窗口 ≥ 2 个大版本。
