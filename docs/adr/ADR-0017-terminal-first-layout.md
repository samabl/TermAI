# ADR-0017：终端为主体、单一侧栏、设置独立窗口、新建终端即标签选择器

- 状态：**Accepted**（发起人认可原型后转正；已落地为 HARNESS **AR-23**，并修订 AR-16 与 AR-22 第 7 条）
- 日期：2025-01-01
- 决策者：项目发起人（提出布局方向）+ Orchestrator（整理为可执行规则）
- 关联：**修订 AR-16**（AI 交互入口顺序中的"侧边面板在右侧、为主场"）、**修订 AR-22 第 7 条**（导航收敛）；不改 AR-01 / AR-03 / AR-06 / AR-14 / AR-20、AR-22 其余各项、ADR-0013/0014/0015/0016
- 实现位置：`prototype/termai-ui-terminal-first.html`（原型）、未来 `web-shell` 的布局层与 `ui-native` 的窗口管理

## 背景与问题

v3 原型（Netcatty 取向视觉）通过评审后，发起人对**信息架构**提出新要求：

> 「终端页改为主体，agent和工作区什么的统一放到侧栏（可选方向），设置为新窗口，新建终端改为新增标签页时选择」

v3 的结构是：顶栏「终端 / 工作区」视图切换 + 右侧常驻 AI 面板 + 顶栏「连接主机 / 新建工作区」按钮。这带来三个问题：非终端内容（工作区卡片网格）会整屏抢占终端；AI 面板与左侧导航形成**两个并行的注意力焦点**；「新建工作区」与「连接主机」把"开一个终端"这件事拆成了两个入口，与用户"加一个标签页"的心智不符。

## 可选方案

| 方案 | 描述 | 结论 |
| --- | --- | --- |
| A 保持 v3 | 视图切换 + 右侧常驻 Agent + 顶栏按钮 | 否决（发起人明确要求终端为主体） |
| B 终端为主体 + 单一侧栏 + 设置独立窗口 + 标签选择器 | 全部非终端内容收进侧栏；设置开新窗口；新建终端走 tab「+」 | **采纳** |
| C 终端为主体，但 Agent 仍常驻右侧 | 保留双栏 | 否决（同时保留侧栏与右栏 = 三个焦点，与"统一放到侧栏"冲突） |
| D 全部收进侧栏，但设置仍占主区 | 半重构 | 否决（设置是最不该占终端像素的表面） |

## 决策

### D1 终端是唯一主体
删除「终端 / 工作区」视图切换；终端网格始终占据主区。工作区、主机、会话的浏览与管理不再占用主区。

### D2 单一侧栏承载全部非终端内容
侧栏 = **图标轨道 rail + 内容面板 panel**：rail 只放图标（带 title + tooltip，无可见文字），分区为 Workspaces / Sessions / **Agent** / Snippets / Themes / Plugins / Audit Log，底部固定 Settings 与「收起侧栏」。panel 显示当前分区内容（Workspaces = 分组卡片/列表；Agent = 原 AI 对话面板全部内容，含绑定指示器与作用域切换）。

侧栏整体可收起（Mod+B），收起后终端全宽。**侧栏固定在左侧**（发起人已确认）；保留「左 / 右」设置项仅供 RTL 语言与个人偏好使用，默认左。

### D3 设置独立窗口
Settings 不占主区，改为在桌面壁纸上打开**独立浮动窗口**（自有交通灯、标题栏、圆角与投影），内容含主题（深/浅/跟随系统）、字号字体、软换行开关、侧栏位置、快捷键表。窗口可关闭；窗口内主题切换**实时联动**主窗口（跨窗口状态广播）。

### D4 新建终端 = 新增标签页时选择
顶栏移除「连接主机」「新建工作区」。tab 条的「+」打开**「新建终端」选择器**：本地 Shell（zsh/bash/fish/pwsh）、SSH 主机（最近/收藏）、容器（docker exec / kubectl exec）、WSL、已保存会话、从模板；支持搜索、↑↓、Enter、Esc。选定后真实新增并激活一个 tab。侧栏 Workspaces 分区保留第二条新建入口。

### D5 窗口控制：真实可用，位置与形态**跟随操作系统惯例**
- 主窗口与设置窗口的**关闭 / 最小化 / 全屏（最大化）**必须是**真实可用控件**（替换当前仅作装饰、`aria-hidden` 的圆点），带 `aria-label` 与 tooltip，键盘可聚焦可操作。
- **位置与形态跟随平台惯例**（发起人确认）：**macOS = 左上角圆点**（红/黄/绿，hover 显出 × / − / ⤢）；**Windows / Linux = 右上角**扁平图标按钮（最小化 / 最大化 / 关闭）。
- 行为要真实：**全屏/最大化** = 窗口铺满视口（去掉壁纸留白与外距），再点还原；**最小化** = 收成可点击的胶囊/缩略条，点击还原；**关闭** = 关闭该窗口（主窗口关闭后保留一个可重新打开的入口，避免原型进入死态）。
- **折中范围**：仅"位置与按钮形态"随平台；窗口圆角、投影与配色仍由设计系统统一（避免维护两套窗口 chrome）。若后续要求完全按平台渲染窗口外观，另开 ADR。
- 设置中提供「窗口控制位置：**跟随平台（默认）/ macOS 式 / Windows 式**」；原型另支持 hash 直达（如 `#platform=mac`），便于评审两种形态。

### D6 保留不变
AR-22 全部视觉与密度规则、AR-06 的 L2 dry-run 审批语义、Agent Scope（跨会话写 P3 起）、终端 `??` 内联入口 + ghost text、PTY Session / Agent Session 双标签、⌘K 命令面板、状态栏。

## 理由

- **终端是主对象**：终端用户 90% 的时间在网格里，任何非终端内容占满主区都是浪费像素；v3 的「工作区」整屏视图只在"找主机"这一瞬有用，却要用户切换上下文。
- **一个焦点胜过两个**：把 Agent 与工作区都收进同一条侧栏，消除"左栏 + 右栏"的双面板争注意力问题。
- **「+」即新建**：Windows Terminal / iTerm2 用户的心智就是"加标签页时选 profile"；把 profile/主机选择放进 tab 选择器比放顶栏按钮更符合直觉，也顺带解决顶栏拥挤（AR-22 第 2 条的目标）。
- **设置是配置面，不是工作面**：独立窗口让它不参与主区布局竞争，也便于多显示器使用。

## 后果

**正面**：终端像素利用率最大化；顶栏只剩面包屑、搜索、侧栏开关与「更多」，拥挤问题根治；新建流程与用户心智一致；设置独立窗口为将来"多窗口工作区"铺路。

**负面 / 必须接受的代价**：

1. **Agent 从常驻变为按需**。AR-16 的原始证据是"AI 若制造第二焦点会被永久关闭"；收进侧栏后，Agent 不再持续可见，**使用率可能下降**，且"随叫随到"的心智必须由终端行首的 `??` 内联入口与快捷键承担。
2. **工作区浏览效率下降**。网格不再有全屏舞台，大量主机/工作区的检索、分组与对比能力需要在侧栏面板内重建（搜索、分组、批量选择）。
3. **跨窗口状态同步成本**。设置窗口与主窗口需要广播主题/字体/语言等状态；多窗口同时打开时的冲突解决与持久化顺序要定义清楚。
4. **可发现性进一步下降**（叠加 AR-22 的图标化）：新建终端、设置、侧栏分区都从"看得见的文字"变成"图标 + 弹层"。

## 反方记录与复议条件

- **反方（UX 研究角色）**：Agent 收进侧栏违反了"AI 必须能被自然发现"的结论。**缓解**：保留 `??` 内联入口为第一入口、为 Agent 分区提供独立快捷键、在首次出现可解释场景时做一次性提示。
- **反方（SRE 角色）**：主机/工作区浏览被压缩到侧栏，多机运维效率下降。**缓解**：侧栏 Workspaces 面板必须支持搜索、分组与键盘导航；保留"展开为大网格"的逃生门（见 Open Questions）。
- **复议条件**：若上线后数据显示 AI 使用率或跨会话操作数显著下降（例如相对 v3 基线下降 >30%），应回退为"Agent 常驻右栏"或提供「Agent 常驻」开关。

## 关联决策与实现位置

- 修订：AR-16（入口顺序中的"侧边面板在右侧"改为"侧栏分区 + 内联入口"，入口**顺序**不变）、AR-22 第 7 条（导航收敛的落点从主导航改为 rail 分区）。
- 不变：AR-06、AR-14、AR-20、AR-22 其余各项、ADR-0013/0014/0015/0016。
- 实现：`web-shell` 布局层（rail/panel/主区）、`ui-native` 窗口管理（设置窗口）、tab 条与「新建终端」选择器（`shell-bridge`）。

## Open Questions

1. **已决议：侧栏固定在左侧**（发起人确认）。AR-16 原文中的「侧边面板在右侧」在本次修订中作废；「左 / 右」设置项保留仅供 RTL 语言与个人偏好，默认左。
2. Agent 是否需要「常驻 / 按需」两种模式（常驻 = 固定在侧栏并默认展开该分区）？
3. 设置窗口是否允许同时开多个？多窗口下的主题冲突以谁为准（最后修改者 / 主窗口优先）？
4. 工作区面板是否需要"展开为大网格"的逃生门（临时占用主区）？
5. 「新建终端」选择器的默认排序：最近使用优先，还是按分组固定顺序？
6. **已决议（发起人选定方案 A）**：窗口控制的**位置与按钮形态跟随平台**（macOS 左上圆点 / Windows·Linux 右上扁平按钮），**窗口外观（圆角 / 投影 / 配色）保持统一**。
   - **否决方案 B**（窗口外观也完全按平台渲染）：最原生，但需为 Windows 维护第二套标题栏与按钮样式，并给 AR-22 的"统一标尺"开平台例外，一致性代价与长期维护成本过高。
   - **复议条件**：若 Windows dogfood 出现明显的"半原生"违和感或误触，再评估方案 B，或退化为"全平台统一 macOS 式左上"。
