# ADR-0021：CI 构建产物输出与 GitHub Action 准入

- 状态：Accepted
- 日期：M0 收口后
- 决策者：Orchestrator（发起人要求「后续 actions 构建需输出产物」；综合 DevEx(09) / 安全隐私(08) / CTO 工程(10) / 内核(04) / 后端平台(06) 评审立场）
- 关联：AGENTS 第 4 节（CI 门禁）、第 5 节（ADR 触发条件：引入新依赖类别）；HARNESS 第 8.1 节（六件套）、第 6.3 节（数据分级）、AR-11（PTY 流/文件/输出/密钥不出设备）、AR-12（遥测与日志纪律）、AR-21（许可与开源）、ADR-0014（平台矩阵与 CI 成本）、ADR-0015（供应链与动作准入）；docs/spec/07 第 1.2 节（构建与工具链锁定）、第 3.4 节
- 影响实现：.github/workflows/ci.yml（windows-build 作业）、tools/kernel-gates/check.mjs（新增 K8）、docs/plan/m0-delivery-report.md 第 6.2 节

## 背景与问题

1. 首次 CI 实跑证明 windows-latest 上能稳定产出三个可执行文件（termai / sessiond / pty_echo），但它们只存在于 runner 的文件系统，push 结束即消失。
2. **发起人要求：后续 Actions 构建必须输出产物。**
3. 现有 ci.yml 自设契约：**只允许 actions/checkout 与 actions/setup-node，不使用其它第三方 action**。要输出产物就必须突破该契约，属 AGENTS 第 5 节的「引入新依赖类别」→ **必须走 ADR**。

## 会议记录（角色立场，保留分歧原文）

| 角色 | 立场 | 关键论点 |
| --- | --- | --- |
| 09 DevEx / 生态 | **支持** | 产物不可取回等于构建不可消费：下游（打包、回滚演练、外部验证者）拿不到二进制，CI 只能证明「能编译」，不能证明「产物可交付」。这属于交付链断裂，而不是便利性缺失。 |
| 10 CTO / 工程 | **有条件支持** | ADR-0014 把「任一 stable 版本 ≤15 分钟全量回滚」写进验收，而回滚需要**可寻址的产物**；同时提醒产物存储与 Windows runner（2 倍计费）都是 ADR-0014 月成本上限内的真实开销。 |
| 08 安全隐私 | **支持但设硬边界** | **公开仓库的 Actions 产物对全世界可下载。** 因此产物只能是构建输出本身：任何日志、门禁报告、会话日志、测试临时文件、含绝对路径或终端内容的文件**一律不得上传**（HARNESS 第 6.3 节：路径与命令输出是 L2 敏感）。另要求产物**可校验**（哈希）与**可追溯**（提交 SHA + 工具链版本）。 |
| 04 内核 | **支持但要求诚实标注** | 三平台产物才是 ADR-0014 的最终形态；当前只出 win32-x64，必须显式登记为临时范围，**不得让「产物已输出」被读成「平台矩阵已达标」**。 |
| 06 后端平台 | **支持，划清边界** | SBOM、签名、SLSA 证明属 G5 / DC-36 范畴，应在 P1 随发布流水线落地；本 ADR 只解决「可下载」，不假装已解决供应链完备性。 |

## 备选方案与被否决项

| 方案 | 描述 | 判定 |
| --- | --- | --- |
| A 不加 action，继续只打印大小 | 保持现有契约不变 | **否决**：不满足发起人要求，产物不可消费 |
| B 用 gh CLI 上传到 GitHub Release | 走 release 语义 | **否决（现阶段）**：M0 无版本号语义，且 release 是契约性发布动作，不应由每次 push 触发 |
| C **actions/upload-artifact@v4** | GitHub 一方 action | **采纳**：与已使用的 checkout / setup-node 同源同信任等级，无需自建存储，无新增云凭据 |
| D 第三方制品库（S3 / Nexus 等） | 外部对象存储 | **否决**：引入云凭据与外部依赖，违背「默认本地、最小暴露」；企业场景应另开 ADR，不在 M0 |
| E 自托管 artifact 服务 | 自建分发 | **否决**：运维成本远超 M0 需求 |

## 决议

### D1 准入 actions/upload-artifact@v4

作为 ci.yml 中**唯一新增**的 action。理由：一方来源、无需外部凭据、与既有两个 action 同信任等级。**代价与改进项**：以版本 tag 固定（与既有约定一致）；**后续应改为 SHA 固定**（供应链加固，建议 P1）。

### D2 产物内容白名单（硬边界）

**仅允许**：target/release 下的 termai.exe、sessiond.exe、pty_echo.exe，以及 SHA256SUMS.txt。
**禁止**：日志、门禁报告 JSON、会话日志（.termai/）、测试临时文件、任何含绝对路径或终端内容者。
依据：公开仓库产物对全世界可下载；HARNESS 第 6.3 节把路径与命令输出列为 L2。

### D3 命名与保留

- name = termai-<version>-win32-x64-<short sha>
- retention-days: 14
- if-no-files-found: error —— **缺产物即失败，不得静默通过**

### D4 可复现与可追溯

构建加 `--locked`；工具链由 rust-toolchain.toml 锁定（1.94.0）；产物附带 SHA-256 校验和；作业输出记录 rustc / cargo 版本。

### D5 常态化规则（对应发起人「后续构建需输出产物」）

**凡承担构建职责的作业必须输出产物**，且由静态门禁 **K8** 校验：workflow 中存在上传步骤、设置 retention-days、path 不含 denylist（target/debug、日志、.termai、通配全仓）。把「要求」变成「机器校验」，而不是一句约定。

### D6 平台范围诚实声明

当前产物**仅 win32-x64**。ADR-0014 要求的 Linux x64 与 macOS arm64 产物**仍未产出**，在此显式登记为未达标（与 K3 的 ConPTY 缺陷同属 P0 出口阻断项）。

## 代价

1. 新增一方 action → 供应链面扩大（缓解：一方来源 + tag 固定 + 后续 SHA 固定）。
2. 产物存储/下载与 Windows runner 均计入 ADR-0014 的成本上限，保留期 14 天是成本与可用性的折中。
3. 公开产物可被他人镜像与再分发。本项目为 Apache-2.0 OR MIT，属预期行为；但**当前产物未签名**，不得被当作官方发布。

## 反方保留与复议条件

- **保留（08 安全）**：即便只上传二进制，未签名产物仍可能被误认为官方发布。**缓解**：产物名含提交 SHA 与平台、保留期仅 14 天，且本 ADR 明示「非官方发布、未签名」。**复议条件**：P1 引入签名 / SLSA Build 证明后，本 ADR 的产物策略必须重审。
- **保留（10 CTO）**：14 天保留期可能与「回滚需要更久」冲突。**复议条件**：若回滚演练证明 14 天不足，延长至 90 天并重做成本评估。
- **反对（严格供应链视角）**：主张只用自建制品库。**否决理由**：M0 引入云凭据与外部存储的复杂度不成立。**复议条件**：P3 出现合规要求（SLSA L3 + 私有 registry）时重评。
