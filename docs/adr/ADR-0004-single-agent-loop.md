# ADR-0004：单 Agent 主循环架构（否决多 Agent 编排）

- 状态：Accepted
- 日期：2025-01-01
- 决策者：Orchestrator（综合 10 角色评审）
- 关联：AR-05；AR-03、AR-17；DC-26、DC-28、DC-29、DC-31；HARNESS §5、§8.2

## 背景与问题
1. 业界默认倾向是「多 Agent 编排」（规划者/执行者/评审者、角色分工图），社区框架成熟、演示效果强。
2. 终端任务的实际特征：粒度小（单命令、单报错）、时延敏感（诊断首 token P95 <3s，§5）、状态高度共享（同一 Pane、同一 cwd、同一 git 工作区）。
3. AR-17 已把价值排序钉死为「故障诊断 > 上下文感知命令生成 > 大规模运维（Phase 4+）」，前两项不需要并行分工。
4. 多 Agent 引入的不确定性：非确定性路由、跨 Agent 上下文复制与漂移、审批归属不清（谁批准了哪一步）、成本与 token 放大。

## 可选方案（至少 2 个，含被否决项）
| 方案 | 主张方 | 否决 / 采纳理由 |
| --- | --- | --- |
| A 多 Agent 编排框架默认开启 | 通用 AI Agent 实践 | 否决。编排开销与不确定性远大于收益；审批链与审计归属会退化 |
| B 纯单 Agent、完全无委派 | 极简倾向 | 否决。长日志分析、多仓库调查等可并行检索任务会阻塞主循环 |
| C 单 Agent 主循环 + 受控子 Agent 委派 | Orchestrator | **采纳**（AR-05） |

## 决策
1. 默认形态为**单 Agent 主循环**：模型 → 工具调用 → 观察 → 再推理（Glossary Agent Loop）。
2. **子 Agent 仅用于可并行、只读、可验证的子任务**：检索、多仓库调查、长日志分析。子 Agent 默认**只读**，不得直接执行副作用操作。
3. 所有副作用（写操作、网络、外发）必须回流到主循环，经统一审批与审计（DC-34：记录操作者、审批人、结果）。
4. **多 Agent 编排框架默认关闭**，不进入默认依赖图；Phase 4+ 若大规模运维确有分工需求，以**显式开关**启用。
5. 工具 ABI 统一（DC-26）：name/json_schema/risk/idempotent/timeout/approval_policy/render_hint，输出统一 envelope；MCP 视为工具来源之一，独立进程沙箱 + Policy Engine 二次校验（DC-28）。
6. 合入门禁：AI 变更必须带离线 eval；「危险命令率上升」即阻断合入（DC-31）。

## 理由
1. 主循环与用户形成「一对一可问责」关系：每次动作都能回答「谁发起、谁批准、结果如何」，多 Agent 会让这条链断裂。
2. 单循环的上下文可以精确裁剪与脱敏（与 ADR-0003 的订阅裁剪配合），避免多份上下文副本导致 secret 泄露面扩大。
3. 收益面（并行检索）用「受控只读子 Agent」即可覆盖，不需要完整编排框架的复杂度预算。

## 后果（正面 / 负面 / 需要接受的代价）
- 正面：审批与审计链清晰；token/成本可控；评测可复现；编译与运行时依赖更少。
- 负面：并行度上限较低，超长任务的墙钟时间可能高于多 Agent；对主循环 prompt 质量要求更高。
- 需要接受的代价：
  1. 必须实现子 Agent 的**只读能力裁剪**与结果回注协议，防止绕过审批。
  2. 用户若强行需要编排，只能等 Phase 4+ 的显式开关——默认体验不提供。
  3. eval 集必须覆盖子 Agent 回注后的上下文一致性（DC-31）。

## 反方记录与复议条件
- **反方（通用 Agent 实践派 / 07 内部少数意见）**：多 Agent 在复杂调查中确实能缩短墙钟时间并提高召回；完全关闭会牺牲极端场景能力。
- **复议触发条件**：Phase 4+ 大规模运维（多主机、多仓库、长日志）出现**显式分工需求**，且实测「主循环墙钟时间 / 用户可接受阈值」不足。此时以显式开关启用，**默认仍关闭**。
- 不可放宽：子 Agent 永不获得直接副作用能力；多 Agent 不得绕过审批或审计。
