## 1. 背景与问题

ADR-0014 的「实现位置」写着 `crates/termai-xtask（bench / perf-gate / matrix / dist / sign）`，并在「关联决策与实现位置」表中再次把 AR-19 的实现位置写成 `termai-xtask perf-gate、bench-report.json`。

**该 crate 不存在**：目录不存在，`Cargo.toml` 中零处提及 xtask（第 142 轮核实）。

**而实际存在、且已被门禁逐字校验的是 Node 工具 `tools/bench/`**：`bench:check`（B1–B8，结构门禁）与 `bench:selftest`（注入故障并证明判定逻辑不是恒绿）都在 CI 中运行。因此 §5 每条指标的测量实现在**名义上有一个不存在的主场、事实上有一个可用的主场**（第 142 轮发现，登记为决策 D-5）。

**这不只是「代码写在哪里」的美观问题**：E-P0-3 的「§5 每条指标的测量实现」是 P0 出口项，而它此前没有权威归属——写入错误的主场意味着重做或分叉。

## 2. 可选方案

| 方案 | 内容 | 结论 |
| --- | --- | --- |
| **A（本 ADR）** | **承认现状：`tools/bench` 为最终主场**；以本 ADR 取代 ADR-0014 的两处实现位置引用 | **采纳**：只动文档，且只动两处；`tools/bench` 已被 B1–B8 逐字校验、并已自证能失败 |
| B | 新建 `crates/termai-xtask`，按 ADR-0014 原计划实现 | **否决**：要重做一遍已被门禁验证的工作（schema 校验、机器指纹、NON_GATING 语义、AR-27 自证），且两套实现并存期间必然分叉 |
| C | 测量实现进 xtask、门禁校验留 Node | **否决**（最危险）：**把实现与校验它的门禁分属两处**，正是 D-4 点名的「两套关于『有效测量』的定义」 |

## 3. 决策

**采纳 A。** `tools/bench/`（Node）是 §5 测量与门禁的最终实现主场；ADR-0014 中 `crates/termai-xtask` 的两处引用（第 7 行与第 285 行）由本 ADR 取代，并在原处标注「被 ADR-0028 取代」。

**代价（如实记录）**：① §5 的测量与门禁实现**不在 Rust 工作区内**，因此不受 `cargo test`/`clippy` 覆盖（其正确性由自身的 self-test 与 CI 步骤保证）；② 若将来确需一个 Rust 侧的性能门禁入口（例如把 G4 的回归判定接进 cargo 流程），那是一个**新**问题，须另立 ADR，**不构成本项的复议理由**。

**复议条件**：若 ① `tools/bench` 的 self-test 被移除或不再在 CI 中运行，或 ② 出现必须由 Rust 侧完成而 Node 无法表达的测量，则本 ADR 应被复议。

## 4. 后果

- **解锁 E-P0-3 的「§5 每条指标的测量实现」**：其归属不再有歧义（此前为 D-5）。
- ADR-0014 的其余内容（平台支持矩阵、机器档位 RM-A/RM-C、AR-19 的「仅绑定机器、不改数值」）**保持有效**，不被本 ADR 触及。
- `docs/plan/p0-open-decisions.md` 的 D-5 随之关闭。
