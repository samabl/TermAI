# ADR-0012：VT 引擎策略、性能预算口径与 a11y 承诺边界

- 状态：Accepted
- 日期：2025-01-01
- 决策者：Orchestrator（综合 10 角色评审）
- 关联：AR-18、AR-19、AR-20；DC-08、DC-13、DC-16、DC-17、DC-37；HARNESS §5、§8.1、§8.2、§11（OQ-06）

## 背景与问题
1. VT 自研程度分歧：04 主张「复用 vte 作基础状态机（fork-pin）+ 自研扩展层，不自研 ESC 解析器」；10 主张「不 fork 现有终端代码，clean-room 自研，以行为测试集为规格」。
2. 性能口径分歧：冷启动 02 ≤100ms vs 04/05/10 ≤150ms；延迟 10 P99 ≤16ms vs 04/05 P99 ≤8ms；对比度 03 ≥7:1 vs 02 ≥4.5:1。多口径会互相掩护。
3. a11y 边界长期模糊：团队倾向承诺「终端完全无障碍」，但语义化 TUI 在技术上不可行（应用自行绘制的字符画没有语义）。
4. 门禁：vttest / esctest / kitty 套件 100%、xterm 兼容 ≥99%；行为回放 ≥99.5%；fuzz 24h 无 crash（§8.1）。

## 可选方案（至少 2 个，含被否决项）
| 方案 | 主张方 | 否决 / 采纳理由 |
| --- | --- | --- |
| A fork vte 并在 fork 内改造 | 04 的强化版 | 否决（作为长期形态）。fork 造成上游差异维护与安全补丁同步负担，架构自主性下降 |
| B 完全 clean-room 自研 ESC 解析器，从零开始 | 10 初版 | 否决（作为起点）。重复已验证的苦力劳动，P0 时间与 fuzz 风险不可接受 |
| C vte 作为**依赖**（非 fork）置于 trait 边界之后 + 自研语义层 + 并行 clean-room 评估 | Orchestrator | **采纳**（AR-18） |

## 决策
1. **VT 引擎（AR-18）**：Phase 0–2 以 **vte 作为依赖**（非 fork）实现基础 ESC 状态机，置于 termai-vt 的 **trait 边界**之后；**OSC / kitty keyboard / iTerm2 / Sixel / grid 语义层自研**。
2. 同时立项 **clean-room 解析器评估**，**仅当** vte 无法承载新协议或上游停滞时，按 trait 边界替换；锁定版本 + 记录上游差异。
3. **性能预算口径（AR-19）**：统一为「**发布门禁**」与「**目标值**」两列（HARNESS §5）；任何单项指标的最坏场景**以门禁为准**，达标余量记为工程债。
   - 冷启动到可输入：门禁 P95 ≤150ms / 目标 ≤100ms。
   - key-to-photon（本地）：门禁 P99 ≤16ms / 目标 P99 ≤8ms（P50 ≤4ms）。
   - 4K@120Hz 网格帧时 <8.3ms（丢帧 <0.1%）；解析+渲染吞吐 ≥500MB/s；空闲 RSS ≤120MB；24h RSS 斜率 <1MB/h。
4. **性能门禁进 CI**：§5 全部门禁项，回归 >5% 阻断合并（§8.1 第 4 条）。
5. **a11y 与 i18n 边界（AR-20）**：
   - 承诺 **UI 层**（Tab/Pane/面板/设置）对 NVDA/VoiceOver 全流程可达（WCAG 2.2 AA）。
   - **不承诺语义化 TUI**，只承诺 **raw 输出朗读 + 应用模式切换**。
   - 核心任务键盘完成率 **100%**；命令面板功能覆盖率 **100%**（CI 校验动作表与菜单差集为空）。
   - i18n v1 即用 ICU MessageFormat；RTL 镜像**不阻塞 v1**，但**网格内 bidi 必须走 Unicode Bidi 算法**。
6. **诚实原则**：所有能力边界必须在产品内明示，不允许用模糊措辞掩盖（AR-20）；对比度正文 ≥4.5:1 为 AA 门禁，官方主题默认目标 ≥7:1 且 CI 校验（DC-13）。
7. PTY/平台：Windows 唯一生产路径 ConPTY（Job Object 管理进程树，Win10 1809 为地板）（DC-16）；渲染 wgpu + rustybuzz/swash，多页字形 atlas，grapheme cluster shaping 再映射列（DC-17）。
8. 持续 fuzz：VT/PTY/IPC/插件消息 ≥10⁸ 次无崩溃，崩溃全部回归（DC-37、§8.1 第 6 条）。

## 理由
1. 分阶段策略同时满足两条正确直觉：不重复已验证的苦力劳动（04），又保住架构自主与可替换性（10）。
2. 门禁 / 目标双列消除了「用目标值互相掩护」的空间，使风险 R7（性能预算渐进侵蚀）可被 CI 直接拦截。
3. 把 a11y 承诺限定在可验证的 UI 层，避免了「承诺后无法交付」的信任损失；同时用 raw 朗读 + 应用模式切换保留实际可用性。

## 后果（正面 / 负面 / 需要接受的代价）
- 正面：P0 交付不被 ESC 解析器阻塞；上游差异可替换；性能口径唯一可验收；a11y 承诺可测。
- 负面：引入第三方依赖带来安全补丁与版本锁定负担；clean-room 评估需要额外投入；不承诺语义化 TUI 会让部分用户失望；不承诺 subpixel AA（ADR-0001）在 Windows 观感受损。
- 需要接受的代价：
  1. 必须维护「上游差异登记」与 trait 边界契约测试，防止 vte 语义泄漏到内核其他模块。
  2. 达标余量（如 P99 8ms → 16ms 之间的部分）被明确记为工程债，而不是可挥霍的冗余。
  3. RTL 镜像不阻塞 v1，但网格内 bidi 必须正确，需要独立的 bidi 测试集。

## 反方记录与复议条件
- **反方（10，保留原文）**：复用 vte 会长期绑住上游节奏，clean-room 才是架构自主与安全可控的终局。
- **反方（04，保留原文）**：不自研 ESC 解析器是理性分工；clean-room 评估可能分散 P0 资源并带来新的兼容长尾（R3）。
- **反方（02/03 冲突面）**：02 的冷启动 ≤100ms 与对比度 ≥4.5:1 更宽松，03 的 ≥7:1 更严；AR-19 以门禁 / 目标两列统一，不再各自宣示。
- **复议触发条件**：
  1. VT 替换：**仅当** vte 无法承载新协议（如 kitty keyboard/iTerm2 扩展）或上游停滞（连续 ≥2 个发布周期无维护），按 trait 边界替换为 clean-room 实现。
  2. 性能门禁放宽：必须附基准数据与 TSC 批准（AGENTS.md §5），且不得放宽 §5 门禁列本身。
  3. kitty keyboard protocol 是否默认开启：**否**，按应用探测后启用（OQ-06，P1）。
- 不可放宽：a11y 边界必须明示；不得承诺语义化 TUI；不得删除 raw 输出朗读能力。
