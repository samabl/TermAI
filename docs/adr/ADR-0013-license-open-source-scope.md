# ADR-0013：许可与开源范围终裁（全栈开源，Apache-2.0 OR MIT）

- 状态：Accepted
- 日期：2025-01-01
- 决策者：项目发起人（经 Orchestrator 确认）
- 关联：AR-21（取代 AR-10 的许可与商业形态部分）、ADR-0008（被本 ADR 取代）、DC-01…DC-40 不受影响
- 实现位置：仓库根 `LICENSE-APACHE` / `LICENSE-MIT` / `README.md`、CI 许可门禁、`docs/spec/07-engineering-quality-and-release.md`

## 背景与问题

ADR-0008 按 AR-10 裁定为 **Open Core**：客户端核心 Apache-2.0，云端服务闭源专有，以「闭源服务 + 开放协议」变现。该方案的前提假设是「终端商业化的可持续分割线在云端」。

项目发起人澄清了一个此前未被显式询问的前提：**TermAI 是一个开源项目**，且开源范围是**全栈（客户端 + 云端服务）**。这使 ADR-0008 的核心前提失效，必须重裁。

## 可选方案

| 方案 | 描述 | 结论 |
| --- | --- | --- |
| A 全栈开源 + Apache-2.0 OR MIT | 客户端、服务端、SDK、协议、工具链统一双许可；收入靠托管/支持/企业服务 | **采纳** |
| B Open Core（ADR-0008 原案） | 核心 Apache-2.0，云端闭源 | 否决（与发起人「开源项目」定位冲突） |
| C AGPL + 商业双许可 | 用传染性强制云端回馈 | 否决（企业采用受阻，与 A1「终端是信任基础设施」冲突） |
| D BSL/SSPL 时间窗 | 云服务 4 年后转开源 | 否决（信任摩擦与法务成本高于收益；且已选择全栈开源） |
| E Apache-2.0 单一许可 | 最主流单一许可证 | 否决（Rust 生态通行「OR MIT」双许可，能给下游最大自由度且无歧义） |

## 决策

1. **许可证**：客户端、服务端、SDK、协议、工具链统一 **Apache-2.0 OR MIT**。CI 校验 SPDX 表达式；仓库根放两个 LICENSE 文件；不强制源文件头。
2. **开源范围**：**全栈开源，不存在闭源云端模块**。官方商业形态为托管、支持订阅、合规与企业服务，源码同样公开；企业专有定制只能以独立插件/独立仓库存在，不得回流核心。
3. **链接边界**：核心链接边界禁 **GPL/AGPL/SSPL**；弱 copyleft（MPL-2.0/EPL-2.0）准入与「链接边界」的 CI 可执行定义由 **ADR-0015** 裁定。
4. **不可变商业承诺**：本地功能永不被远程锁死；插件市场 v1 零抽成、无 DRM；主题格式与商店永久免费；不出售用户数据。

## 理由

- 终端是**信任品**，采用门槛由发行版与企业法务决定；宽松双许可是唯一能让「内核 + 插件生态 + 企业嵌入」同时成立的组合。
- 「OR MIT」在 Rust 生态是事实标准，消除单一许可的选择成本，且不产生语义歧义（区别于「双许可 + 商业授权」模式）。
- 全栈开源把竞争维度从**许可护城河**转为**生态规模与上下文质量**，这与 AR-17（差异化在诊断与上下文）自洽。

## 后果

**正面**：最大化采用与插件生态；企业法务几乎零阻力；社区可直接审计云端数据流，强化 AR-11 隐私承诺的可信度；协议与 SDK 的开放承诺不必再打折。

**负面 / 必须接受的代价**：

- 竞品可整体 fork 并托管我们的服务端。
- 收入完全依赖执行（托管质量、支持响应、合规能力），许可不再提供缓冲。
- 云端服务开源后，安全漏洞披露面扩大（对应 §6 供应链与 SDLC 要求更严）。
- 需要新增 CI 许可合规流水线（SPDX 白名单 + 链接边界判定），见 ADR-0015。

## 反方记录与复议条件

- **反方（06 云端架构师，支持 B）**：Open Core 的收入结构更稳；全栈开源削弱云端差异化。**保留意见**：若 18 个月内官方托管收入无法覆盖控制面成本，可复议把**运营侧工具**（部署/计费/SRE 工具，非客户端、非用户数据面）转为专有。
- **反方（02 UX 角色曾主张编排层 AGPL）**：缺少传染性保护会被白嫖。**接受其风险**：以生态速度而非许可设壁垒。
- 复议条件必须同时满足：TSC 2/3 多数 + 90 天公示（AGENTS.md §5），且不得触碰「不可变商业承诺」四条。
