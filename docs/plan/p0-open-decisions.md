# P0 三个待决策项（决策简报）

> 用途：这五项**不是实现问题**，而是**判定域/能力声明**问题。**在它们被追认之前**，G1 台账里有一批失败**既不能算缺陷、也不能算已解决**。
> 每一项都给出：**被阻塞的条数 → 选项 → 后果 → 建议 → 依据**。**建议不等于决定**；决定权在对应 owner（`kernel/01` owner / 产品与 UX）。
>
> **证据与入口（先读这条链）**：**当前状态与逐项归属**见 `docs/audit/debt-p0.md` 第一段（入口段）；**D-1/D-2/D-3 的数字来源**见 `docs/audit/esctest-classification.md` 与 `docs/audit/esctest-failing-index.md`（机器产物，268/268 定位）；**怎么跑、怎么验**见 `docs/plan/p0-verification-runbook.md`；**D-5 涉及的那条 ADR 分歧**见 `docs/audit/debt-p0.md` 第 142 轮记录；**顶层计划**见 `docs/plan/p0-delivery-plan.md`。
>
> 现状口径：**267 passed / 41 known-bug / 259 failed / substitutions 0**（同一调用、可复现）。

## D-1 `SD-23`：HARNESS §7「esctest 全通过」的**判定域**（子集 vs 全集）

**被阻塞**：**约 69 条**（未登记扩展族 41 + 查询类 20 + xterm 专有 8），另加颜色 45、`XtermWinops` 19 的归属。

**两种读法**：
| 读法 | 含义 | 后果 |
| --- | --- | --- |
| **A（字面）** | 每条 esctest 用例都必须通过 | 必须实现全部 xterm 扩展；**与我方冻结的 `kernel/01` §3.5「OSC 52 读取永不实现」直接矛盾** |
| **B（子集 + 差异）** | 「全通过」判定在已声明子集上；子集外按 **K-04** 进差异登记（最小复现 + 依据 + 豁免期限） | 上面约 69 条进差异表；**通过率的分母口径必须同时定义** |

**建议：采 B。** 依据：**A 与自身冻结条款矛盾**——若「全通过」= 全集，则我方已声明的「OSC 52 读永不实现」使 P0 **在构造上不可能达成**。**B 不是降低标准，而是把「不做」变成可审计的登记**（K-04 要求逐条附依据与期限）。

**需要 owner 补的**：① 判定域的明文表述；② **通过率分母口径**（子集内分母 vs 全集分母）；③ K-04 差异表的**双签人**（当前无 TSC，OQ-19 未决）。

## D-2 颜色查询的**能力声明**（`OSC 4 / 10 / 11 / 12`）

**被阻塞**：**45 条**（`ChangeColor` / `ChangeDynamicColor` / `ChangeSpecialColor` / `ResetColor` / `ResetSpecialColor`）。

**现状**：这四个序列**不在** `kernel/01` §3.5 子集内；我们**一律不应答**，`esctest` 因此超时失败。

| 选项 | 含义 | 代价 |
| --- | --- | --- |
| **① 不应答（现状）** | 保持沉默 | 45 条按 D-1 的 B 读法进差异表；**代价 0，诚实** |
| **② 声称 xterm 默认 256 色并应答** | 报一套标准调色板 | **在终端尚无颜色渲染时报调色板＝能力声明**；若渲染出来与所报不符，**违反 AR-20 诚实原则** |
| **③ 实现颜色渲染后再应答** | 先有渲染，再谈声明 | 正确顺序，但**属 P1/P2 范围**，不解决 P0 |

**建议：P0 采 ①（保持不应答 + 登记差异）**；把「终端调色板是什么」作为**渲染可用之后**的独立决策。**依据**：AR-20；且**当前没有任何颜色渲染**，报调色板无法自证。

## D-3 `DA` / `DA2` / `DECID` 的**设备身份**

**被阻塞**：**约 4–6 条**（`DATests` 2、`DA2Tests` 2、`DECIDTests` 1；`DECID` 是 DA 的过时形式）。

**现状**：`csi_dispatch` **没有 `CSI c` 分支** → 完全不答设备属性；而 `vte_adapter` 把 `c` 计为「已知」（计数与行为不一致，应顺手修正）。

| 选项 | 含义 | 代价 |
| --- | --- | --- |
| **① 报告自身真实身份**（VT 级别 + 自有扩展） | 诚实 | esctest（`--expected-terminal xterm`）**这 4–6 条仍失败** → 进差异表 |
| **② 声称 xterm 兼容身份** | 可让这几条通过 | **该声明必须有真实兼容度支撑**；当前 esctest 267/259，**尚无资格声称** |

**建议：采 ①**，并在实现 DA 时**把身份字符串写进 ADR**（对外契约）。**依据**：AR-20；且 ② 的收益（4–6 条）远小于它带来的契约风险。

## D-1…D-3 之间的关系（D-4 / D-5 见文末，与本节的取舍无关）

**D-1 是总开关**：它决定 D-2、D-3 的结果是「缺陷」还是「已登记的偏差」。**建议先用一次评审同时定掉 D-1，再据其读法定 D-2/D-3**——否则会出现「同一个东西在两张表里归类不同」的自相矛盾。

## 不在本简报内的两项（属设计，不属判定）

- **`XtermWinops` 19 条**：需要「应用可请求 resize」的**动态 resize + reflow 策略**（连动 `kernel/03`）。**属设计任务**：先定策略（滚动区域/光标/软换行/备用屏在 resize 时的语义），再实现。
- **`DECRQM` 25 条**：**oracle 分歧**（SD-22），需 **xterm 实现或 ctlseqs 原文条款**才能判定；**目前环境拿不到**（网络受限），故**保持 Pm=0 不改**。
## D-4 §8.2 可靠性测量的归属与报告口径（sessiond 重建 P95 ≤2s / P99 ≤5s）

**被阻塞**：**E-P0-4 的最后一项验收**（AR-26 第 4 条；`HARNESS.md:259`）。

**为什么它是一个决策而不是一个实现**：该验收出自 **§8.2 可靠性**，而 **kernel/06 全文没有出现「重建 / reconnect」**——**§8.2 的时序测量目前没有规定的归属、格式与判定人**。**同时它绝不能进 §5 的注册表**：`tools/bench/registry.mjs` 是 HARNESS §5 十九行的**逐字转录**，**由门禁 B1/B3 每次重新解析文档并逐字比对**，**加一行「重建」既是假转录、也不会被验证**。

| 选项 | 含义 | 代价 |
| --- | --- | --- |
| **A 扩展 kernel/06 覆盖 §8.2** | 在既有方法学内增加一节「可靠性时序测量」，**复用**既有 `bench-report` schema、机器指纹（§3.7）、NON_GATING 语义（ADR-0014）与 AR-27 自证 | **需要一次规范修订并由 owner 追认**；收益是**不出现第二套「什么算有效测量」的定义** |
| **B 另设 §8.2 口径** | 独立格式与流程 | **两套测量规范并存**，日后必然分叉；且要重新回答机器绑定、NON_GATING、可复现性自证等同样的问题 |
| **C 人工流程** | 参考机上按文档化步骤人工测并记录 | **最省事，但 E-P0-4 的「可执行证据」退化为人工记录**，与全项目自动化门禁的口径不一致 |

**建议：A。** 依据：**bench 那套（机器指纹、NON_GATING、AR-27 自证、报告 schema）已经存在且被门禁验证**；为 §8.2 **重建一遍**会立刻产生「**两套关于『有效测量』的定义**」——**而这正是本项目最不该出现的分叉**（第 30 轮我建议「测量落 tools/bench」时其实已经直觉地选对了容器，**只是没意识到它需要一个 §8.2 的口子**）。

**需要 owner 补的**：① kernel/06 是否增加 §8.2 一节；② 若增加，**§8.2 行的机器绑定与 NON_GATING 规则**是否与 §5 相同；③ **判定人**（当前无 TSC，OQ-19 未决）。

**在定案前**：**不写任何 §8.2 测量代码**，也不得在 `SECTION5_MAPPING` 中新增行（那会破坏 B1/B3 的转录校验）。
## D-5 §5 测量实现的主场：ADR-0014 的 xtask，还是既有的 Node tools/bench

**被阻塞**：**E-P0-3 的「§5 每条指标的测量实现」（第 142 轮发现）**。

**事实（已核实）**：**ADR-0014 的实现位置一行写着 `crates/termai-xtask（bench / perf-gate / matrix / dist / sign）`，而该 crate 不存在**（目录不存在、`Cargo.toml` 零提及）；**实际存在且已被门禁验证的是 Node 工具** `tools/bench`（B1–B7 + `--selftest` + `--report` + `--machine`）。

| 选项 | 含义 | 代价 |
| --- | --- | --- |
| **A 以 Node `tools/bench` 为最终主场** | 承认现状 | **需一次新 ADR 取代 ADR-0014 的那一行**（并在旧条目上标注「被 ADR-xxxx 取代」——AGENTS §5 禁止改历史）；**收益是只有一个「什么算有效测量」的定义** |
| **B 新建 `crates/termai-xtask`** | 按 ADR 原计划 | **要重做一遍已被门禁验证的东西**（schema 校验、机器指纹、NON_GATING、AR-27 自证），**且两套实现并存期间必然分叉** |
| **C 测量实现进 xtask、门禁校验留 Node** | 各取一半 | **最危险**：**实现与校验它的门禁分属两处**，正是 D-4 里点名的「两套关于『有效测量』的定义」 |

**建议：A。** 依据：**`tools/bench` 是既存在、又被 CI 逐字校验（B1/B2/B3）且已自证能失败（`bench:selftest`）的那一个**；**B 要求把这份已被验证的工作重做一遍**；**C 会立刻制造 D-4 已经警告过的分叉**。**A 的唯一代价是一次 ADR 更替——而这不是障碍，是本项目处理「推翻旧决策」的标准动作。**

**⚠ 本项与 D-1…D-4 不同类，因此不必等 TSC（第 174 轮辨析）**：**D-1/D-2/D-3 决定「什么算通过」（§7 G1 的判定域、能力声明、设备身份），D-4 决定 §8.2 指标的口径——按 AGENTS §5「指标变更：任何 §5 预算或 §8 门禁的放宽，必须附基准数据与 TSC 批准」，**它们都需要 TSC，而 `C1` 记录 TSC 未成立**，因此这几项是**结构性阻塞**，不是排期问题。**而 D-5 是「实现写在哪里」的归属问题**，**正确工具是 ADR（AGENTS §5 的 ADR 触发条件：新增/删除模块、改变对外契约），不是 §5/§8 的放宽**——**因此它可以由负责人按正常工程程序推进：写一份新 ADR 取代 ADR-0014 的实现位置一行，并在旧条目上标注「被 ADR-xxxx 取代」。** **它一经定案，就解锁 E-P0-3 的「§5 每条指标的测量实现」**——**即：五项决策里有一项不依赖缺失的 TSC，而它恰好挡着一块真实的 P0 工作。**

**需要 owner 补的**：① 是否以新 ADR 取代 ADR-0014 的实现位置一行；② 若采 A，**§5 测量的实现是否也随之落到 `tools/bench`**（还是仍需要一个 Rust 侧的性能门禁入口）。

**在定案前**：**不写任何 §5 测量代码**（与 D-4 同一条理由）。
